# Automic Vault Source

## Scope

This directory contains primary application code for Automic Vault and Nucleus.

Components:
1. Nucleus
   - A multi-source package manager for Homebrew, npm, and PyPI packages.
   - Installs as root to `/opt` and stubs in `/usr/local/bin`.
   - Fast, secure, and optimized for an agentic world.
   - Written in Rust.
   - Keep coverage above 80%.
2. Automic Vault.app
   - A macOS application for managing Nucleus.
   - Written in Swift/Objective-C with Cocoa/AppKit, not SwiftUI.
3. Website package origin
   - The Rust `av-web` service now lives in `../av.www`.
   - Package database generation now lives in `../av.db`.
   - Do not reintroduce website-origin server code under `src/`.

Commit as Codex after each completed job.

## Architecture First

Before editing code, identify:
- the user-facing surface being changed
- the runtime boundary involved
- the persistence boundary involved
- whether the change is additive, behavioral, or structural

Prefer preserving established boundaries over introducing new abstractions.

## Runtime Boundaries

Be explicit about what runs where.

- `src/nucleus/` is the Nucleus CLI runtime.
- `src/lib/rs/` is shared Rust code used by multiple source modules.
- `src/gui/` is the macOS Cocoa/AppKit application.
- `src/helper/` is privileged/helper code and its launch/XPC support.
- `../av.www/crates/av-web/` is the `av-web` Atlas package-origin service. It
  owns package page routing, rendering, markdown alternates, package sitemaps,
  package CSS/JS, and `/pkg/search.json`.

Keep GUI code, helper code, CLI code, and shared library code physically
separate. Do not make server or request-time assumptions unless the source tree
already has that runtime.

## Package Origin Data

- `av-web` reads `pkg.sqlite` from `AV_WEB_DB_PATH`; the production default is
  `/var/lib/automic-vault-web/pkg.sqlite`.
- The local artifact is generated by `../av.db/scripts/generate-pkg-sqlite.py`
  and deployed with `../av.www/scripts/deploy-pkg-origin.sh`.
- Website package search is curated server-side search over SQLite rows.
- Keep `/db.json` as the public compatibility contract. The package SQLite
  artifact is private server data and should not cause public schema version
  bumps.

## Security

- Nucleus must not expose runtime-configurable install roots or package metadata
  endpoints. Keep production paths and trusted upstreams hard-coded.
- Release builds install under `/opt` and stub into `/usr/local/bin`.
- Debug builds install under `/tmp/opt` and stub into `/tmp/usr/local/bin`.
- Treat new configurability surfaces as security-sensitive because they can
  introduce exploit vectors.
- Secrets go in `.envrc`, and `.envrc` must stay ignored by git.

## Persistence Boundaries

Treat persisted data shape as architecture.

- Keep schema-touching code easy to find.
- Keep migrations, seed data, and sync scripts discoverable.
- Prefer additive database or file-format changes unless explicitly doing a
  migration.
- Do not casually rename or repurpose persisted fields.
- Preserve backward compatibility for public data formats and APIs when
  practical.

If the source code uses SQLite or local files, assume single-node constraints
matter unless documented otherwise.

## File Layout

- Keep entrypoints thin. Commands and flags should usually be handled in the
  entrypoint file.
- Put business logic in reusable modules.
- Keep route definitions, persistence code, and rendering/view code separate
  when those concepts exist.
- Prefer one file per broad responsibility over giant mixed-purpose files.
- When a module becomes hard to scan, split by responsibility, not by pattern.
- Shared utilities belong in `src/lib/` only when used by multiple modules.

## Tool Choices

Use the simplest toolchain already present in the repo.

### Rust

- Prefer `cargo test`, `cargo fmt`, and `cargo clippy` when configured.
- Keep reusable Rust code in `src/lib/`.

### Swift, Objective-C, and Cocoa

- Keep the GUI in AppKit/Cocoa conventions already used by the app.
- Do not introduce SwiftUI.
- Keep UI work off the main thread when it can block.
- No click should ever feel like nothing happens; if work cannot complete
  instantly, show progress, a spinner, or another visible pending state.
- The main thread can never block more than 8.5ms.

### Shell and Operational Code

- Operational shell scripts belong in `scripts/`, not under `src/`, unless they
  are source-owned helper fixtures.
- Scripts should be non-interactive when possible.

Do not add heavy new infrastructure without a clear need.

## Dependency Policy

Prefer:
- standard library
- existing repo dependencies
- small, well-scoped libraries

Avoid adding dependencies for:
- trivial parsing
- small helper functions
- thin wrappers over built-in capabilities

When adding a dependency, keep the reason local and obvious. Justify the new
dependency choice in the root `README.md` under `## Dependencies`.

## Component Versioning

- GUI and CLI tools all have the same version from root `Cargo.toml`.
- Helpers and protocols have their own versions and must be bumped
  independently when their interface changes.
- `NUKE_BUILD_ID` is an automatic exact-build stamp, not a manually bumped
  compatibility version. Production builds should derive it from the Git commit;
  local debug GUI builds may use a stable local value to avoid unnecessary Rust
  rebuilds.
- Bump `NUKE_PROTOCOL_VERSION` in root `.env` and
  `PROTOCOL_VERSION` in `src/lib/rs/core.rs` when the `av serve` protocol
  contract changes. This includes method names, request params, response
  payloads, required fields, error semantics the GUI depends on, socket
  lifecycle, or daemon compatibility expectations. Do not bump it for internal
  implementation changes that preserve the wire contract.
- Bump `NUKE_HELPER_VERSION` in root `.env` whenever privileged helper behavior
  changes, even if the XPC/protocol interface is unchanged. Installed helpers
  are only replaced when the bundled helper version is newer.

## Generated and Checked-In Artifacts

- `target/`, caches, and temporary outputs are generated artifacts.
- Do not edit generated files unless the repo intentionally treats them as
  source.
- If a generated file is committed, update the source that produces it when
  possible, then regenerate.

## Testing and Verification

Before finishing substantial source work, run the smallest relevant
verification:
- targeted tests first
- then broader checks if needed
- then a build if the change affects packaging or deployability

Prefer fast local verification over exhaustive but slow workflows.

## Change Discipline

Prefer:
- additive changes
- narrow diffs
- preserving public contracts
- preserving file layout conventions

Avoid:
- opportunistic rewrites
- introducing new frameworks casually
- moving many files without architectural benefit
- mixing unrelated refactors into feature work

## Quick Start for Agents

When starting work in `src/`:
1. Scan the nearby module that owns the responsibility.
2. Identify the runtime and persistence boundaries involved.
3. Make the smallest change that fits the current structure.
4. Verify with the narrowest relevant command.

## Versioning

- `NUKE_BUILD_ID` is an automatic exact-build stamp. Do not manually bump it.
  Release and publish builds should derive it from the Git commit; local debug
  builds may use a stable local value to avoid unnecessary Rust rebuilds.
- `NUKE_PROTOCOL_VERSION` tracks the `av serve` protocol contract. Bump it when
  the GUI/helper protocol surface changes, including method names, request
  params, response payloads, required fields, error semantics depended on by the
  GUI, socket lifecycle, or daemon compatibility expectations.
- `NUKE_HELPER_VERSION` tracks the installed privileged helper. Bump it whenever
  privileged helper behavior changes, even if the XPC/protocol interface did not.

## Localization

The app is localized, user-visible strings should be added to
`src/gui/Resources/`.
